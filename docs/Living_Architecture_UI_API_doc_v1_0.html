Arhitectură vie (UI + API)

Acest ghid păstrează contractele esențiale UI, API, de raportare și testare din arhitectura v1.0 arhivată. Le reconciliază cu framework-ul modular curent. Numele păstrat al fișierului identifică filiația documentului, nu o nouă versiune a bibliotecii sau o dovadă de execuție.

Documentul HTML asociat prezintă aceleași secțiuni în panouri pliabile și diagrame statice. Acest document Markdown deține conținutul; metadatele HTML consemnează numele fișierului sursă și SHA-256 normalizat. Actualizează-le împreună. Arhitectura definește harta concisă a modulelor, Testare definește strategia, colecția de comenzi definește rețetele de execuție, iar feedback-ul gestionează criteriile nerezolvate. Ghidul nu consemnează acceptanță nouă a aplicației.

Diagramele HTML late păstrează dimensiunea nativă a etichetelor. Derulează în interiorul figurii pentru o secvență lată; pagina rămâne lizibilă.

Matricea de browser menținută definește versiunile fixate Selenium/browser/driver/CDP și pregătirea portabilă a binarelor. Căile proiectului provin din rădăcina reactorului sau din intrări explicite ale apelantului/mediului; căile absolute de execuție se rezolvă din aceste intrări când un API le cere.

2) Configurație centralizată

Încărcare și precedență

ConfigManager încarcă framework.properties din classpath sau un fișier explicit selectat prin -Dframework.properties=.... Sursa împachetată responsabilă este atf-core/src/main/resources/framework.properties. Încărcarea la execuție nu caută un arbore sursă monolitic. Proprietățile JVM individuale suprascriu cheile încărcate.

Folosește get(key, default) pentru valori opționale și require(key) pentru valori obligatorii nevide. Accesul și validarea configurației aparțin opțiunilor tipizate Core; pașii aplicației nu trebuie să dubleze interpretarea. Setările explicite ale mediului, cache-urile browserelor și selecția suitei rămân responsabilitatea apelantului. Nu pune acreditări sau căi presupuse ale unei mașini în exemplele publicate.

Configurație UI

Valori implicite UI menținute 
base.url=https://practicesoftwaretesting.com

ui.window.size=

ui.engine selectează un furnizor instalat playwright sau selenium. Descoperirea nu pornește un browser. Furnizorii absenți sau duplicați produc diagnostice; indisponibilitatea unui adaptor nu justifică selectarea tacită a altui motor.

Dimensiunea explicită validă a ferestrei are prioritate. Altfel, rezolvarea folosește o dimensiune utilizabilă a sistemului, cu 2560x1440 ca alternativă când execuția este fără interfață sau sistemul nu oferă o dimensiune utilizabilă. Alternativa nu promite că fiecare sesiune configurată are acea dimensiune. Zoomul se normalizează la nivelurile acceptate: valoarea configurată 60 devine 67. Navigarea și capturile păstrează zoomul rezolvat. Pregătirea browserelor și selecția Node implicită a SDK-ului sunt descrise în Testare.

Numărul maxim de reîncercări la limitarea ratei trebuie să fie nenegativ. Zero permite cererea inițială fără reîncercări; valorile negative eșuează înaintea execuției.

Aceste URL-uri sunt valori implicite, nu autorizare pentru modificarea unei aplicații. Fluxurile API de scriere cer un token explicit utilizabil. BaseTestAPI sare inițializarea orientată spre scriere dacă tokenul este gol; omiterea nu înseamnă acceptanță. Fixture-urile anonime/cu autentificare invalidă controlate de apelant folosesc căile explicite de cerere destinate lor. Autentificarea obișnuită este centralizată în ApiClient; utilitarele speciale de autentificare negativă sunt suport de test, nu un al doilea mecanism de autentificare de producție.

Core poate executa fără o implementare a raportării. Instalarea atf-reporting oferă Extent prin serviciul neutru ReportingBackend. Setarea susținută este reporting.engine=extent; motoarele nesusținute eșuează explicit, iar căile rapoartelor rămân relative la modulul executant dacă nu sunt suprascrise.

4) Reguli canonice de execuție

MUST și MUST NOT de mai jos sunt reguli de revizuire cu domeniu delimitat. Nu implică existența unui control automat pentru fiecare afirmație. Harta verificării identifică responsabilii actuali ai surselor/testelor; acceptanța nerezolvată rămâne în feedback.

Principii păstrate și execuție UI auditabilă

Titlurile v1.0 arhivate definesc filiația acestor douăsprezece principii păstrate. Intenția lor rămâne obligatorie în stratul declarat. Deciziile reconciliate explică regulile literale înlocuite; eliminarea unei restricții de implementare depășite nu elimină obligația privind responsabilitatea, adevărul eșecului sau dovezile.

MAINTAINED înseamnă că sunt identificați responsabilul sursei curente și o verificare existentă. Nu înseamnă că verificarea s-a executat, că fiecare ramură este acoperită sau că o aplicație publică a acceptat scenariul. PARTIAL expune o obligație cunoscută neîndeplinită. Pasul validării declară așteptarea, citește valoarea observată și deține aserțiunea și verdictul final PASS/FAIL. Comportamentul negativ așteptat al aplicației poate trece testul numai când respingerea așteptată este observată independent. Un eșec neașteptat de browser, acțiune, aserțiune sau configurație își păstrează rezultatul real eșuat sau omis; consemnarea metadatelor contractului nu îl poate certifica.

Responsabilul guvernanței principiilor living LivingPrinciplesGovernanceTest verifică cele douăsprezece ID-uri, căile reale către surse/verificări și stările delimitate. Principiile absente sau duplicate și promovarea lacunei declarate de curățare sunt eșecuri de diagnostic. Aceste controale structurale nu stabilesc completitudinea semantică și nu înlocuiesc acceptanța nativă a produsului.

Limitele configurației și raportării

Validarea UI respinge booleenii malformați și așteptările din afara intervalului 1..2147483 secunde întregi înaintea achiziției furnizorului. Cele șase opțiuni UI folosesc un cititor comun de booleeni; WaitUtils folosește cititorul validat de așteptare. Precedența cheii canonice și a celei vechi și valorile implicite valide rămân neschimbate. Vezi contractul Core.

  • MUST păstra un singur încărcător de configurație Core și folosi responsabilii opțiunilor sale tipizate.
  • MUST direcționa raportarea semantică a execuției prin StepLogger/ReportLogger.
  • MUST păstra importurile SDK Extent în atf-reporting și importurile SDK de browser în adaptorul corespunzător.
  • MUST NOT permite unui pas de afaceri să instanțieze un adaptor de raportare sau să controleze începutul/sfârșitul/scrierea completă a testului. Ciclul de viață aparține ascultătorului/implementării.
  • MAY publica evenimente neutre de execuție din adaptoare prin publicatorul Core; aceasta nu oferă adaptorului acces la StepLogger sau la mecanismele interne ale implementării.

Interacțiuni UI, selectori și dovezi

Fluxurile aplicației folosesc UIActions generice și responsabili reutilizabili de pagini/validări. UIEngine oferă capabilități de browser precum interacțiuni, citiri, așteptări, capturi și observarea răspunsurilor de rețea; nu implementează regulile de afaceri ale clienților sau comenzilor. Testele de adaptor/contract ale framework-ului pot exercita direct UIEngine pentru această limită. Nu sunt exemple pentru stratul aplicației.

Preferă locatori CSS semantici stabili. Folosește vocabularul de locatori acceptat și potrivirea exactă a textului/identității când este necesară. XPath este potrivit când expresia CSS/semantică acceptată nu poate exprima relația necesară. Nu deduce paritatea browserelor numai pentru că același șir se compilează.

Dovezile observate MUST proveni din elementul sau răspunsul potrivit. Un ID de creare identifică factura dorită; nu demonstrează prezența în lista clientului. Valoarea persistată a stării, eticheta afișată și identitatea rândului sunt observații separate. Un utilitar de înregistrare trimite o singură identitate o singură dată; trebuie să expună rezultatul eșuat în loc să înlocuiască tacit acel client.

Așteptări, reîncercări și temporizare

UIActions aplică așteptări în funcție de motor: Selenium declară supportsAutoWait=false, iar Playwright declară true. Condițiile explicite comune folosesc WaitUtils și timpul-limită configurat. Mecanismele interne ale adaptoarelor pot implementa așteptarea nativă; vechea regulă generală care interzicea orice așteptare în afara WaitUtils nu descrie sursa curentă.

WaitUtils furnizează observații și aruncă o excepție când o condiție obligatorie nu este îndeplinită; poate adăuga detalii unui pas activ, dar nu emite independent FAIL. Acțiunea/validarea înconjurătoare deține verdictul. Preferă finalizarea observabilă și un timp-limită delimitat în locul pauzelor fixe. Utilitarele curente de pauză și așteptările vechi nu dovedesc temporizare deterministă; evaluează-le în testele existente.

Interogarea repetată API și reîncercările la limitarea ratei au politici separate. Păstrează aserțiunile exacte pentru furnizor/încercări, rezultatul final și cazul negativ de expirare. O reîncercare nu stabilește că o operație ne-idempotentă a fost anulată sau poate fi repetată sigur. Nu schimba așteptările, reîncercările sau valorile așteptate numai pentru a obține o rulare verde.

Responsabilitatea validării și aserțiunilor

Validările aplicației compară valori reale observate independent cu contractul de afaceri așteptat și produc dovezi utile la eșec. Reutilizează responsabilul validării în loc să împrăștii aserțiuni de afaceri prin servicii. Testele de framework/unitate își afirmă direct contractele tehnice; nu trebuie să treacă fiecare aserțiune printr-o clasă de validare a produsului.

Un eșec de afaceri trebuie să rămână un test eșuat. Continuarea testelor independente ulterioare este politica executantului/suitei, nu permisiune de a ascunde eșecul original. Fixture-urile cu eșec așteptat trebuie să declare rezultatul așteptat și să păstreze un criteriu separat; un FAIL produs intenționat într-un raport nu înseamnă automat eșecul regresiei exterioare.

Contractul StepLogger

Operațiile publice acceptate includ:

StepLogger.startStep(String title);
StepLogger.logDetail(String detail);
StepLogger.logCodeBlock(String content);
StepLogger.pass(String message);
StepLogger.fail(String message, Throwable failure);
StepLogger.fail(String message, String stacktraceAsText);
StepLogger.step(String title); // returns an AutoCloseable StepScope

Detaliile și operațiile finale necesită un pas activ. Contextul pasului este ținut pe fir și curățat la limitele testului. Adâncimea imbricată a pașilor este acceptată; regula arhivată care interzicea întotdeauna un al doilea pas activ este depășită. Apelanții trebuie să închidă domeniul deținut și să evite publicarea finală duplicată. StepScope își protejează propriile operații close/pass/fail.

Un StepScope nefinalizat înregistrează un diagnostic și își închide adâncimea; nu fabrică un verdict de afaceri trecut. Implementarea curentă nu impune global un apel final exact o dată în fața utilizării arbitrar incorecte de către apelanți. Folosește regresiile existente pentru ciclul de viață în loc să documentezi o promisiune mai puternică decât oferă sursa.

Restricții globale și de modul

Bibliotecile de producție necesită dependențele lor de execuție. Lombok la compilare și dublurile/verificările destinate testelor au domenii distincte intenționate. atf-tests depinde de biblioteci în domeniul de test; interdicția arhivată asupra tuturor dependențelor de test și modulelor Maven separate nu se aplică.

Păstrează contractele publice mici, evită suprascrieri accidentale ale metodelor de ciclu de viață/monitor ale Object și explicitează responsabilitățile. Guvernanța surselor trebuie să examineze toate rădăcinile modulelor de producție, profilurile, tipurile importate/calificate și referințele simple relevante. Un arbore sursă copiat sau un nume de fișier potrivit nu demonstrează o direcție validă a dependenței.

Pașii apelurilor HTTP păstrează faptele cererii/stării/răspunsului; pașii validării explică așteptarea și comparația observată. Utilitarele de curățare/interogare repetată au propriul domeniu și nu trebuie confundate cu acceptanța completă a aplicației.

Ciclu UI, capturi la eșec și stare finală

Închiderea clasei curăță starea interacțiunilor în finally după orice rezultat al închiderii motorului. Eșecurile achiziției eliberează numai resursele obținute, în ordine inversă, păstrând eșecul primar și cauzele distincte suprimate de curățare. Testele de componentă existente pentru bază și furnizori verifică aceste căi fără pornirea browserelor; acceptanța nativă și cea de produs rămân separate.

Legendă: relații și limita dovezii

Motoare, adaptoare și protejarea eșecului

Extent implementează ReportLogger prin ReportingBackend instalat. Deține nodurile explicite, pașii semantici, atașamentele și scrierea completă/finalizarea. Implementarea și selecția susținută a motorului rămân în atf-reporting, accesate prin fațadele Core.

6) Organizarea și cerințele testelor

Scenarii UI și responsabilitatea ciclului de viață

Clasele UI ale aplicației folosesc BaseTestUI sau un ciclu de viață intenționat, revizuit de responsabil. Compun servicii/acțiuni/pagini/validări de produs în locul apelurilor SDK de browser. Testele framework/native pot deține direct fixture-uri ușoare de motor; nu sunt obligate să lanseze aplicația sau să extindă clasa de bază a produsului.

Exemplul istoric de înregistrare era /auth/register, cu rezultate pozitive și negative. Păstrează intenția verificând comportamente de afaceri relevante și variante de eșec, fără a afirma un număr universal arbitrar de teste sau a impune înregistrarea fiecărui test UI fără legătură. Regresiile păstrate ale înregistrării acoperă o identitate/o trimitere și erori vizibile.

Scenarii API, independență și curățare

Testele API ale aplicației dețin entitățile create și rămân independente de ordinea metodelor. Un scenariu GET/update/delete creează entitatea necesară; curățarea nu înlocuiește tacit criteriul său de afaceri. Un scenariu complet de ciclu de viață distinge crearea, citirea, actualizarea, ștergerea și verificarea ștergerii. Fixture-urile comune trebuie să declare ciclul de viață și limitele curățării.

Exemplele arhivate folosesc următoarele operații de serviciu:

POST   /public/v2/users       -> creation contract
GET    /public/v2/users/{id}  -> retrieval contract
PUT    /public/v2/users/{id}  -> replacement contract
PATCH  /public/v2/users/{id}  -> partial update contract
DELETE /public/v2/users/{id}  -> deletion contract

Stările/conținutul așteptate provin din contractul țintei selectate, nu din această listă ilustrativă de endpoint-uri. Validarea schemei JSON aparține validării răspunsului într-un pas relevant. O listă de metode nu demonstrează acoperirea endpoint-urilor, iar o dublură locală nu demonstrează acceptanța serviciului public.

Date de test, autentificare și fixture-uri negative

Datele reutilizabile de fixture aparțin atf-tests/src/test/resources/tests/testdata și fabricilor/constructorilor lor. DataGenerator existent deține valorile unice ale aplicației. JSON este formatul păstrat pentru exemplele comune de produs; testele unitare pot folosi dubluri în memorie, iar testele negative pot cere date literale malformate. Vechea cerință ca fiecare valoare din fiecare test să provină din JSON nu este un invariant global valid pentru regresiile framework-ului.

Furnizează autentificarea la execuție. Nu lipi tokenuri reale în documente, fixture-uri înregistrate sau exemple de raport. Utilitarele de autentificare negativă pot selecta explicit autentificarea absentă/invalidă; nu schimbă identitatea configurată în spatele apelantului unui utilitar pozitiv. Inspectează ipotezele existente privind conturile demo înainte de execuția controlată a aplicației.

Criterii observabile și limite oneste de execuție

Regresiile existente trebuie să distingă valori așteptate și observate, să păstreze calea negativă și să eșueze când comportamentul protejat este eliminat. Aserțiunile privind forma sursei protejează arhitectura; nu înlocuiesc comportamentul la execuție. Nu transforma un eșec în omitere, nu relaxa valoarea așteptată, nu șterge cazul negativ și nu crește timpii-limită fără o cauză diagnosticată și un responsabil.

Folosește selecțiile menținute locale, de browser și agregate descrise în Testare. Delimitează separat rezultatele: contractele native, fixture-urile locale, fixture-urile în browsere reale și scenariile controlate de aplicație răspund unor întrebări diferite. Domeniul curent al mentenanței păstrează inventarul E2E existent și îmbunătățește stabilitatea framework-ului, documentația și guvernanța. Registrul de feedback gestionează deciziile de domeniu și dovezile matricei browser/CDP. Fixture-urile locale nu stabilesc acceptanța aplicației publice.

7) Artefacte de livrare și execuție

Artefactele menținute obligatorii includ POM-urile părinte/module, README-urile modulelor, framework.properties Core, sursele bibliotecilor, resursele/suitele de test și perechea ghidului arhitecturii. JAR-urile de execuție conțin clasele proprii și descriptorii serviciilor. atf-tests ține sursele de verificare și nu oferă un API de framework pentru producție. Consumul curent înlocuiește coordonata monolitică istorică descrisă în migrarea consumatorului.

Rulează comenzile pentru 7) Artefacte de livrare și execuție 
mvn -B -ntp verify
mvn -B -ntp -Pbrowser test
mvn -B -ntp -Paggregate test

Rulează comenzile numai dintr-o copie temporară pregătită pentru validare. Instalarea browserelor, filtrele de clasă, cache-urile și locațiile rezultatelor sunt documentate în Testare. Păstrează dovezile în afara surselor de dezvoltare/live. Consemnează selecția reală, punctul sursei, stările și artefactele; o rulare omisă sau copiată nu este o execuție reușită.
