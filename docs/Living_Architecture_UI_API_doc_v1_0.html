Living Architecture (UI + API)

This guide preserves the essential UI, API, reporting and test contracts from the archived v1.0 architecture. It reconciles them with the current modular framework. The retained filename identifies the document lineage, not a new library release or an execution receipt.

The HTML companion presents the same sections with collapsible panels and static diagrams. This Markdown document owns the content; the HTML metadata records its source filename and normalized SHA-256. Update both together. Architecture owns the concise module map, Testing owns strategy, the command cookbook owns execution recipes, and feedback owns unresolved criteria. This guide records no fresh application acceptance.

Wide HTML diagrams retain their native label size. Scroll inside the figure to inspect a wide sequence; the surrounding page remains readable.

The maintained browser matrix owns the Selenium/browser/driver/CDP pins and portable binary preparation. Project paths derive from the reactor root or explicit caller/environment inputs; absolute runtime paths are resolved from those inputs when an API requires them.

2) Centralized configuration

Loading and precedence

ConfigManager loads framework.properties from the classpath, or an explicit file selected by -Dframework.properties=.... Its packaged source owner is atf-core/src/main/resources/framework.properties. Runtime loading does not search a monolithic source tree. Individual JVM properties override loaded keys.

Use get(key, default) for optional values and require(key) for nonblank required values. Configuration access and validation belong to Core typed options; application steps should not duplicate parsing. Explicit environment settings, browser caches and suite selection remain caller-owned. Do not place credentials or assumed machine-specific paths into published examples.

UI configuration

Maintained UI defaults 
base.url=https://practicesoftwaretesting.com

ui.headless=true
ui.window.mode=fullscreen
ui.window.size=
ui.page.zoom.percent=60
ui.wait.timeout.seconds=20
ui.screenshots.enabled=true
ui.screenshots.on.failure.only=false
ui.screenshots.capture.final.state=true

ui.engine selects an installed playwright or selenium provider. Discovery does not start a browser. Missing or duplicate providers produce diagnostics; an unavailable adapter is not a reason to silently select another engine.

An explicit valid window size takes precedence. Otherwise the resolver uses a usable system size, with 2560x1440 as the headless/unavailable-system fallback. That fallback is not a promise that every configured session has that size. Zoom is normalized to supported levels: the configured 60 resolves to 67. Navigation and screenshots preserve the resolved zoom. Browser preparation and SDK-default Node selection are covered in Testing.

The maximum rate-limit retry count must be nonnegative. Zero permits the initial request without reattempts; negative values fail before execution.

These URLs are defaults, not authorization to mutate an application. API write flows require an explicit usable token. BaseTestAPI skips its write-oriented setup when that token is blank; a skip is not acceptance. Caller-controlled anonymous/invalid-auth fixtures use the explicit request paths designed for them. Normal authentication is centralized in ApiClient; special negative-auth helpers are test support, not a second production authentication mechanism.

Core can execute without a Reporting backend. Installing atf-reporting enables its Extent/Allure implementation. The two report engines are selected by reporting.engine behind one ReportingBackend service and the neutral facade; invalid engine configuration is a diagnostic, not a documented universal NO-OP fallback. Report directories are relative to the executing validation module unless overridden.

4) Canonical execution rules

MUST and MUST NOT below are scoped review rules. They do not imply that every statement has an automatic guard. The verification map identifies current source/test owners; unresolved acceptance stays in feedback.

The reconciled decisions explain superseded literal rules; removing an obsolete implementation constraint does not remove its ownership, failure-truth or evidence obligation.

It does not mean that a check was executed, that every branch was covered, or that a public application accepted the scenario. PARTIAL exposes a known unfulfilled obligation. Execution evidence belongs to its exact source, selection, engine and native result in the report publication.

For each selected UI scenario, the action step records intent, locator and the reportable input; password/secret-labelled values are represented by [REDACTED] while the original value still reaches the browser. This bounded classification does not inspect arbitrary application fields or sanitize SDK exception text. A final artifact review must check the actual generated evidence for unintended sensitive values.

The validation step states the expectation, reads the observed value and owns the assertion and terminal PASS/FAIL. Expected negative application behavior can pass its test only when that expected rejection is independently observed. An unexpected browser, action, assertion or configuration failure retains its actual failed or skipped result; recording contract metadata cannot certify it.

The documentation governance owner checks the twelve IDs, real source/check routes and bounded states. Missing or duplicate principles and promotion of the declared cleanup gap are diagnostic failures. These structural guards do not establish semantic completeness or replace native product acceptance.

Configuration and reporting boundaries

UI runtime validation rejects malformed boolean values and waits outside 1..2147483 whole seconds before provider acquisition. The six UI flags share one boolean reader; WaitUtils shares the validated wait reader. Canonical and legacy wait precedence and valid defaults remain unchanged. See the Core configuration contract.

  • MUST keep one Core configuration loader and use its typed option owners.
  • MUST route semantic execution reporting through StepLogger/ReportLogger.
  • MUST keep Extent/Allure SDK imports inside atf-reporting and browser SDK imports inside the corresponding adapter.
  • MUST NOT let a business step instantiate a reporting adapter or control test start/end/flush. Lifecycle ownership belongs to the listener/backend.
  • MAY publish neutral runtime events from adapters through the Core publisher; this does not grant an adapter access to StepLogger or backend internals.

UI interactions, selectors and evidence

Application workflows use generic UIActions and reusable page/validation owners. UIEngine provides browser capabilities such as interaction, reads, waits, screenshots and network-response observation; it does not implement customer or order business rules. Framework adapter/contract tests may exercise UIEngine directly to test that boundary. They are not application-layer examples.

Prefer stable semantic CSS locators. Use the supported locator vocabulary and exact text/identity matching when required. XPath is appropriate when the supported CSS/semantic expression cannot express the needed relationship. Do not infer browser parity merely because the same string compiles.

Observed evidence MUST come from the matched element or response. A creation ID identifies the desired invoice; it does not prove that the invoice appears in the customer's list. Persisted status value, display label and row identity are separate observations. A registration helper submits one identity once; it must expose a failed result instead of silently replacing that customer.

Waits, retries and timing

UIActions applies engine-aware waits: Selenium reports supportsAutoWait=false, while Playwright reports true. Shared explicit conditions use WaitUtils and the configured timeout. Adapter internals may implement their native waiting mechanism; the old blanket rule forbidding every wait outside WaitUtils is not a description of the current source.

WaitUtils supplies observations and throws when a required condition is unmet; it may append detail to an active step but does not independently emit FAIL. The enclosing action/validation owns the verdict. Prefer observable completion and a bounded timeout to fixed sleeps. Current pause helpers and legacy waits are not evidence of deterministic timing; evaluate them in their existing tests.

API polling and rate-limit retries have separate policies. Preserve the exact supplier/attempt assertions, terminal result and negative timeout case. A retry does not establish that a non-idempotent operation was rolled back or safe to repeat. Do not change waits, retries or expected values only to obtain a green run.

Validation and assertion ownership

Application validations compare independently observed actual values with the expected business contract and produce useful failure evidence. Reuse the validation owner instead of scattering business assertions through services. Framework/unit tests assert their own technical contracts directly; they are not required to route every assertion through a product validation class.

A business failure must remain a failed test. Continuing later independent tests is a runner/suite policy, not permission to swallow the original failure. Expected-failure fixtures must declare their expected outcome and preserve a separate oracle; a deliberately produced report FAIL is not automatically a failed outer regression.

StepLogger contract

The supported public operations include:

StepLogger.startStep(String title);
StepLogger.logDetail(String detail);
StepLogger.logCodeBlock(String content);
StepLogger.pass(String message);
StepLogger.fail(String message, Throwable failure);
StepLogger.fail(String message, String stacktraceAsText);
StepLogger.step(String title); // returns an AutoCloseable StepScope

Details and terminal operations require an active step. Step context is held per thread and cleared at test boundaries. Nested step depth is supported; the archived rule that a second active step is always forbidden is obsolete. Callers must close the scope they own and avoid duplicate terminal publication. StepScope guards its own close/pass/fail operations.

An uncompleted StepScope logs a diagnostic and closes its depth; it does not manufacture a passed business verdict. The current implementation does not globally enforce an exactly-once terminal call across arbitrary caller misuse. Use existing regressions to protect lifecycle behavior rather than documenting a stronger guarantee than the source provides.

Global and module constraints

Production libraries require their runtime dependencies. Compile-time Lombok and test-scoped test doubles/checks have intentional distinct scopes. atf-tests depends on libraries in test scope; the archived prohibition on all test-scoped dependencies and separate Maven modules does not apply.

Keep public contracts small, avoid accidental overrides of Object lifecycle/ monitor methods, and make ownership explicit. Source governance must examine all production module roots, profiles, imported/qualified types and relevant simple type references. A copied source tree or matching filename does not prove a valid dependency direction.

The Core TestListener is the stable facade. atf-reporting supplies ReportingTestListener through ReportingBackend and owns session/group/invocation state, attachments, flushing and runtime audit. BaseTestUI/BaseTestAPI declare the Core listener; they do not import AllureTestNg. Native Allure TestNG service discovery belongs to the Reporting dependency. An exception outside an action step is handled at the test lifecycle boundary. Its existence must not be lost because no semantic step was open. Configuration failures, skipped cases and controlled failure simulations remain distinguishable from ordinary successful execution. Optional diagnostic/publication failures are recorded separately from the business outcome.

UI lifecycle, failure screenshots and final state

Class teardown clears interaction state in finally after every engine shutdown outcome. Provider acquisition failures release only acquired resources in reverse order, preserving the primary failure and distinct suppressed cleanup causes. The existing base/provider component tests exercise these error paths without starting browsers; native browser and product acceptance remain separate.

BaseTestUI initializes/quits the engine once per class with always-run teardown. It does not orchestrate report sessions. Failure/final-state registries invoke the UI attachment handler. ScreenshotManager attaches at most once per invocation after a successful capture/attachment; without an active engine/logger it does not manufacture evidence.

The final diagram arrow attempts shutdown; the note identifies independent cleanup in finally. DriverManager removes its engine reference and BaseTestUI clears interaction state even when quit throws. The existing F-011 component oracle checks success, RuntimeException and Error, exact cause identity and repeated teardown. Always-run scheduling alone does not establish these guarantees. This framework-state contract is separate from LD-11's application-data cleanup obligation and from browser-process acceptance.

Failure capture is configuration-dependent. Eligible success can also capture the final UI state when screenshots are enabled, failure-only mode is disabled and final-state capture is enabled. The old rule saying screenshots occur only on FAIL is no longer valid. Retain the complete screenshot, current zoom and its test identity; do not treat a viewport crop or another test's image as proof.

Engines, adapters and fail-safety

Extent and Allure implement ReportLogger behind the installed ReportingBackend. Extent manages its explicit report nodes and flush/finalization. Allure's native TestNG integration owns its test lifecycle while the adapter publishes semantic steps and structured evidence. Backend implementations and engine selection remain inside atf-reporting, reached through Core facades.

Nonblocking diagnostics preserve optional publication/attachment problems without rewriting the original business outcome. This is not a guarantee that invalid configuration, missing required providers or every I/O failure is ignored. Inspect diagnostics and actual artifacts as well as the runner exit code. Adding an engine is a future implementation change; this guide adds no engine.

Core console/diagnostic helpers can emit framework diagnostics; the archived absolute claim that no component except StepLogger ever writes a console message is not a current source invariant.

6) Test organization and requirements

UI scenarios and lifecycle ownership

Application UI classes use BaseTestUI or an intentional owner-reviewed lifecycle. They compose product services/actions/pages/validations rather than browser SDK calls. Framework/native tests can own lightweight engine fixtures directly; they are not forced to launch an application or extend the product base class.

The historical registration example was /auth/register, with positive and negative outcomes. Preserve that intent by verifying meaningful business behavior and failure variants, not by asserting an arbitrary universal test count or making every unrelated UI test navigate to registration. The retained registration regressions cover one identity/one submission and visible errors.

API scenarios, independence and cleanup

Application API tests own their created entities and remain independent of method order. A GET/update/delete scenario creates the entity it requires; cleanup does not silently replace its business oracle. A complete lifecycle scenario distinguishes creation, retrieval, update, deletion and verification of deletion. Shared fixtures must declare their lifecycle and cleanup limits.

The archived examples use these service operations:

POST   /public/v2/users       -> creation contract
GET    /public/v2/users/{id}  -> retrieval contract
PUT    /public/v2/users/{id}  -> replacement contract
PATCH  /public/v2/users/{id}  -> partial update contract
DELETE /public/v2/users/{id}  -> deletion contract

Expected statuses/content come from the selected target's contract, not from this illustrative endpoint list. JSON schema validation belongs to response validation inside a meaningful step. A list of methods does not prove endpoint coverage, and a local mock does not prove public-service acceptance.

Test data, authentication and negative fixtures

Reusable fixture data belongs under atf-tests/src/test/resources/tests/testdata and its factories/builders. Existing DataGenerator owns unique application values. JSON is the retained data format for shared product examples; unit tests may use in-memory doubles, and negative tests may need literal malformed data. The old requirement that every value in every test must come from JSON is not a valid global invariant for framework regressions.

Supply authentication at runtime. Do not paste real tokens into documents, committed fixtures or report examples. Negative-auth helpers can explicitly select missing/invalid authentication; they do not change the configured identity behind a positive helper's caller. Inspect existing demo-account assumptions before controlled application execution.

Observable oracles and honest execution scope

Existing regressions should distinguish expected and observed values, retain the negative path and fail when the protected behavior is removed. Source shape assertions protect architecture; they do not replace runtime behavior. Do not convert a failure to a skip, loosen the expected value, delete the negative case or increase timeouts without a diagnosed cause and owner.

Use the maintained local, browser, Allure and aggregate selections described in Testing. Scope results separately: native contracts, local fixtures, real-browser fixtures and controlled application journeys answer different questions. The current maintenance scope keeps the existing E2E inventory and improves framework stability, documentation and governance. The feedback register owns scope decisions and browser/CDP matrix evidence. Local fixtures do not establish public application acceptance.

Required maintained artifacts include the parent/module POMs, module READMEs, Core framework.properties, owned library sources, test resources/suites and the paired architecture guide. Runtime JARs contain their owned classes and service descriptors. atf-tests holds verification sources and no production framework API. Current consumption replaces the historical monolithic coordinate as described in consumer migration.
