Generated Test Code Review pentru clase create de agenti

Skill analysis-only pentru review de calitate cod pe testele generate. Primeste un folder de teste, citeste codul sursa si layerele folosite, apoi produce un raport HTML care explica daca testele sunt coerente, business-grouped, arhitectural curate si usor de reorganizat.

5. Reorganizare recomandata pentru teste generate
5.1 Forma tinta 
src/test/java/com/ai/ui/tests
  account | checkout | support | admin | catalog | common
    <BusinessObject><LifecycleOrBoundary>Tests

src/test/java/com/ai/api/tests
  users | posts | comments | auth | common
    <Resource><ContractOrLifecycle>Tests

src/main/java/com/ai/ui/support
  flows        // reusable UI workflow services, no assertions hidden in core
  pages        // UI page/screen surface
  validation   // business-visible UI assertions
  model        // UI data/state records
  factory      // UI test data builders/factories
  utils        // low-level UI helpers only when reusable

src/main/java/com/ai/api/support
  client       // HTTP mechanics outside api.core
  service      // API resource service
  steps        // reusable API flow steps
  validation   // response/schema/business assertions
  model        // request/response records
  factory      // payload builders/factories
  utils        // serialization/wait/data utilities

src/main/java/com/ai/ui/core
src/main/java/com/ai/api/core
  protected framework contracts; generated packages must not modify these roots
Numele sunt exemple de forma, nu business obligatoriu. Regula este: pachetele se organizeaza dupa flow-uri si obiecte reale, nu dupa run id-uri sau dupa istoria generatiei MCP. Testele stau in src/test; suportul reutilizabil sta in src/main; core-ul framework-ului nu devine loc pentru helper-e de pachet.

6. Exemple bune si rele
6.1 Bun
  • O clasa are un singur obiect business central.
  • Testul descrie actor, intentie, obiect si rezultat.
  • Actiunile UI sunt delegate catre actions/services.
  • Validarile business sunt in layer de validation.
  • Repetitiile sunt extrase in fixtures/helpers clare.
  • Suportul UI/API nou sta in pachetele main/support potrivite, nu in core protejat.
6.2 Rau
  • Clasa combina invoice, support, profile si admin doar pentru ca au fost generate in acelasi run.
  • Testul foloseste direct engine/selectors pentru business assertions.
  • Metodele sunt numite run03Test2 sau validatesScenario.
  • Fiecare run copiaza aceleasi 40 de linii de setup.
  • Agentul modifica MCP, ATF core, atlas, ui.core, api.core sau ui.engine ca sa treaca pachetul.
  • Refactor plan-ul spune “clean up tests” fara clase/metode concrete.
